# Модель доверия и ограничения

Стенд предназначен для одного доверенного пользователя и его тестовых репозиториев. Он не обеспечивает изоляцию недоверенных проектов друг от друга.

## Что ограничивается

- LLM возвращает данные; внешние записи выполняются API- и Function-блоками.
- Запись разрешена в отдельную AI-ветку целевого репозитория.
- Служебные CI-пути и секреты исключены из генерируемых изменений.
- Исправление связано с текущим SHA PR; устаревшее предложение не должно перезаписывать изменённую ветку.
- Число repair ограничено; повторный запуск без изменения кода разрешён только для распознанного инфраструктурного сбоя.
- Существующие pytest-функции защищены от удаления в цикле исправления.
- Merge выполняется вручную, права на `main` настраиваются в Gitea.

Эти проверки уменьшают область допустимых действий, но не доказывают корректность или безопасность сгенерированного приложения. Проверка наличия теста также не доказывает качество его утверждений.

## Runner

В Talos-манифесте используется privileged Docker-in-Docker. Job исполняет код приложения и может получить доступ к секретам задания, сети и ресурсам, доступным runner. Удаление лишних Kubernetes RoleBinding и отключение service-account token устраняют ненужный прямой доступ к API, но не делают privileged Pod безопасной песочницей.

Для существующего старого стенда простой apply нового манифеста не удалит прежний RoleBinding: его нужно отдельно инвентаризировать и убрать после проверки, что старое Kubernetes-развёртывание приложения больше не используется.

Не подключайте этот runner к внешним fork PR или общедоступной многопользовательской Gitea. Для такого сценария нужны отдельные эфемерные исполнители, минимальные права, сетевые ограничения и воспроизводимые негативные испытания.

## Ключи и сеть

PAT хранятся в Gitea/SIM Secrets. Настоящие `.env`, kubeconfig, talosconfig и содержимое `generated/` не входят в Git. Секреты, попавшие в журнал, следует отозвать; очистка самого текста журнала не возвращает ключу доверие.

Ollama обрабатывает запросы локально, однако это не равно отсутствию исходящего трафика у всего стенда. Загрузка моделей, образов, пакетов и правил анализаторов требует сети. Полная offline-работа и проверенный запрет egress не заявляются.

Talos-пример использует HTTP и NodePort в лабораторной сети. Он не предназначен для публикации сервисов в Интернет. Привязку Ollama к внешнему интерфейсу ограничивайте firewall только нужной подсетью/узлом.

## Legacy loopback proxy

`30-sim-gitea-loopback-proxy-patch.yaml` добавляет sidecar с фиксированным upstream Gitea и ограничением путей `/api/v1/` и `/api/packages/`. Он слушает только loopback внутри Pod. Переключатель `ENABLE_GITEA_LOOPBACK_PROXY` по умолчанию выключен.

Proxy нужен только для старой SIM-конфигурации, где HTTP-блок блокирует приватный адрес Gitea. Он сознательно создаёт отдельный маршрут к внутреннему сервису и должен быть доступен только доверенным workflow. Это не универсальная защита SSRF. Не отключайте глобальную проверку адресов ради одного подключения.

## Что ещё не доказано

Нет подтверждённых негативных испытаний доступа AI-кода к job credentials, внешней сети и Kubernetes host. Нет HA, независимого аудита или сертификации. Внешние образы по умолчанию не везде закреплены digest. Для промышленного применения эти вопросы требуют отдельной работы, а не только изменения настроек модели.

О найденной уязвимости см. [SECURITY.md](../SECURITY.md).
