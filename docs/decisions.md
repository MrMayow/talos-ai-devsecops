# Основные решения

## Четыре workflow вместо одного длинного

Требования, архитектура, реализация и анализ CI имеют разные входы и точки остановки. Разделение позволяет повторить один этап, проверить контракт и сохранить результат согласования. Недостаток — больше связей, ID и версий артефактов, которые нужно поддерживать согласованно.

## Структурированные ответы модели

Workflow ожидают JSON Schema, а не извлекают файлы из свободного Markdown. В strict текст требований рендерится детерминированно из JSON. Это упрощает проверку обязательных полей, но не устраняет обрыв ответа и смысловые ошибки. Поэтому используются ограничения контекста, валидаторы и repair.

## Generic Packages для передачи контекста

Большие требования и архитектуру неудобно передавать копированием между формами. Артефакты публикуются с версией запуска; следующий этап получает ссылку. Обратная сторона — права Packages, owner и доступность Gitea становятся частью рабочего контракта.

## Один повторный CI на исправление

Файловое API может создавать несколько commit для одной правки. Запуск CI на каждый промежуточный commit приводил бы к проверке неполных состояний и гонкам callback. Поэтому после записи итогового набора файлов используется один явный dispatch. Цена — ручной commit в открытый PR тоже требует явного запуска проверки.

## Два профиля

Strict сохраняет reviewers, согласование кода и дополнительные gates. Demo сокращает маршрут для показа процесса, разделяет генерацию приложения, тестов и документации и не останавливает каждую правку CI на согласование. Оба используют один pipeline, но одинаковый зелёный CI не означает одинаковую глубину проверки требований.

## Talos и локальная модель

Talos даёт управляемую через API основу Kubernetes с небольшим набором компонентов ОС. Для лаборатории выбран один узел; отказоустойчивость этим решением не обеспечивается. Ollama работает вне VMware, чтобы использовать GPU Windows без passthrough.

## Ручной merge

Результат модели и зелёный CI не дают достаточного основания автоматически принимать изменение в `main`. Последнее решение оставлено человеку. Проверку прав технической учётной записи нужно выполнять средствами Gitea, а не только указанием в prompt.
