# Проверочный сценарий

Это инструкция для живой SIM/Gitea-лаборатории. Локальные unit-тесты проверяют отдельные функции и контракты; весь маршрут требует работающих сервисов, модели и настроенных ключей.

## Задача

Вставьте в Workflow 01:

> Сделай небольшое REST API калькулятора на Python 3.12 и FastAPI. GET /health возвращает {"status":"ok"}. POST /calculate принимает left и right от -1000000 до 1000000 и operation: add, subtract, multiply или divide. При делении на ноль верни 400, некорректные типы и неизвестную операцию отклоняй. Добавь pytest-тесты и руководства пользователя, администратора и разработчика. Не добавляй базу данных и внешние сервисы.

Эталонный небольшой API с такими endpoint находится в [examples/calculator-api](../examples/calculator-api/README.md). Он нужен для проверки инструментов; результат генерации может отличаться по структуре и реализации.

## Успешный путь

1. Требования сформированы и показаны на согласование. Проверить approve, затем отдельно проверить revise и reject на другом тестовом запуске.
2. Архитектура содержит приложение, обнаруживаемые pytest-тесты и документацию. Утвердить её.
3. В strict проверить предложение кода и согласовать запись. В demo код проходит предзаписные проверки автоматически.
4. Найти ветку `ai/<run_id>` и соответствующий открытый PR. Убедиться, что `main` не изменена.
5. Сопоставить head SHA PR с checkout и SHA в CI summary.
6. Проверить pytest, Semgrep, runtime smoke, ZAP и публикацию отчётов.
7. При зелёном CI убедиться, что Workflow 04 не вызван.
8. Проверить PR вручную. Merge не должен происходить автоматически.

## Исправление ошибки

В одноразовом тестовом PR внесите маленькую ошибку в разрешённый файл приложения. Например, верните неправильную сумму, оставив корректный тест. Вызовите `workflow_dispatch` с исходными `context_version` и `run_id`, `repair_attempt=0` и номером PR.

Сначала используйте `AI_REVISE_DRY_RUN=true`: Workflow 04 должен получить traceback и предложить конкретное изменение без записи. После проверки повторите на тестовом PR с `false`.

Ожидаемый результат: новый commit в той же ветке, тесты не удалены, один повторный CI на итоговый head. При повторных ошибках номер repair увеличивается; после пятой попытки автоматический цикл прекращается.

## Отказы, которые нужно проверить

| Ситуация | Ожидаемое поведение |
|---|---|
| Не настроен PAT или неверный owner Packages | Явная ошибка; процесс не считается успешным |
| Модель вернула пустой/обрезанный JSON | Остановка до записи файлов |
| Предложен путь `.gitea/workflows/pipeline.yml` | Изменение отклонено |
| Изменился PR head между анализом и записью | Старое исправление отклонено |
| pytest не обнаружил ни одного теста | Красный gate и исправление тестов |
| Исправление удаляет существующую `def test_*` | Запись отклонена |
| Callback SIM недоступен | Job остаётся красным при обязательном callback |

## Что сохранить

Для одного прохода достаточно номера PR, run_id, исходного и итогового SHA, статусов этапов, номера repair и обезличенных отчётов. Отдельно запишите решения человека. Не публикуйте ключи и полный необработанный execution export.

Если какого-то шага не было, отметьте его как не выполненный. Успешный возврат `Needs Human` от workflow не означает, что ошибка приложения исправлена.
